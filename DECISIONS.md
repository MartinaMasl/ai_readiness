# Decisions

- 2026-10-15: Hosting on Cloudflare Workers (Python Workers) with FastAPI. Reason: chosen by the author. Minimal example in `worker/`.
- 2026-10-15: `index.html` moved to `worker/public/index.html` and served at `/` as a static asset; the FastAPI app is under `/api`. Reason: author's choice, so the report page is on the main URL with no copy step.
- 2026-10-15: Temporary "API test" button at the bottom of `index.html` that calls `POST /api/echo`. Reason: author wants to check the page can reach the API. Remove before the real report.
- 2026-10-15: LangGraph test on Python Workers (no decision yet). The current LangGraph (1.2.x) cannot be installed: it needs `ormsgpack`, which has no Pyodide build. LangGraph 0.4.3 (2025, with langchain-core 0.3) installs and ran a small ask/check/score graph with a follow-up loop under `pywrangler dev`. The test endpoint was removed afterwards.
- 2026-10-15: The flow is written in plain Python, not LangGraph. Reason: only an outdated LangGraph version runs on Python Workers, and because Workers keep nothing between requests the state must be loaded from and saved to D1 by our own code anyway, so LangGraph would add a dependency without saving work. Plain code is also easier to describe in the thesis. Decided by the author.
- 2026-10-15: A subdimension is scored only on the answers given in its own section, not on anything the respondent said earlier in the conversation. Reason: decided by the author, so each score can be traced to the answers to that subdimension's questions.
- 2026-10-15: The rubric moved from `methodology.json` to `worker/src/rubric.json`, and `wrangler.jsonc` has a rule that bundles `.json` files. Reason: a Python Worker only includes files from `src/`, and by default only `.py` files (tested: a JSON file next to the code was not found without the rule). Decided by the author.
- 2026-10-15: Scores are calculated with Python's `Fraction` (exact arithmetic) and turned into floats only for display. Reason: a float mean can come out as 2.9999999… and be floored to the wrong level; a fraction cannot.
- 2026-10-15: The rubric loader checks that every level table (scale, report_levels, subdimension levels) has exactly the levels 0 to 5. Reason: a mistake in the rubric file fails when the Worker starts, not during a conversation.
- 2026-10-15: The report JSON contains no subdimension scores, only the gap texts. Reason: subdimension scores must not be shown to the respondent, and anything in the JSON could be seen in the browser.
- 2026-10-15: `result.html` is a copy of the design in `index.html` with the example values replaced by empty fields that a short script fills from the report JSON. Dimension cards use one `<template>` copied per dimension, so the number of dimensions comes from the rubric. `index.html` stays unchanged until the chat page replaces it in step 3.
- 2026-10-15: Until D1 exists, the report endpoint only knows two made-up ids: `demo` (real rubric, worked example scores) and `demo-four` (Data texts copied as placeholders for the other three dimensions, so the radar chart has four axes). Both are removed in step 3.
- 2026-10-15: Open question to the author: the main gap is shown as "Now: <current level description> Next level: <next level description>" using the full rubric texts; the design showed one short custom sentence. A dimension or overall score that cannot be calculated is shown as "n/a" / "Not available", which the design does not cover.
- 2026-10-15: No evidence at all now gives a score of 0 (flag `insufficient_evidence`), instead of leaving the subdimension out of the mean. The rule `insufficient_evidence` in the rubric was changed accordingly. Reason: the author wants every dimension and the overall score to always have a value in the report. Consequence: "no evidence" and "evidence of no capability" both give 0; the log shows which one it was (evidence "no evidence" for every criterion). The scoring code no longer handles missing scores; a report with a subdimension not yet scored is an error.
- 2026-10-15: The main gap is shown as one sentence from a new rubric field `gap` (levels 0 to 4 per subdimension), for example "Ownership is informal; the next level requires assigned, documented owners." Reason: the full level descriptions made the cards too long; the author wanted one sentence like in the design. The sentences were drafted by Claude from the level descriptions and must be reviewed by the author, since they are methodology texts. Replaces the open question above.
- 2026-10-15: Step 3, fake chatbot. `flow.py` contains the real flow logic (follow-up loop limited by `max_follow_ups`, next subdimension, finish) with two fake functions, `fake_check` (first answer: nothing covered, one follow-up about the first criterion; second answer: everything covered) and `fake_score` (fixed levels 4, 2, 5 by position). Reason: the whole flow, D1 storage and report can be shown without a model; step 5 replaces only these two functions.
- 2026-10-15: D1 has two tables, `conversations` (state as JSON, loaded and saved on every request) and `logs` (log as JSON, written at the start and after every subdimension). Tables are created by `worker/migrations/0001_create_tables.sql`. Reason: Workers keep nothing in memory between requests; one JSON column per conversation is the simplest structure that holds everything.
- 2026-10-15: Each transcript message in the state carries the name of its subdimension. Reason: the log entry for a subdimension and (later) the scoring prompt use only that subdimension's messages.
- 2026-10-15: `index.html` is now the chat page, in the same style as the report. The original design is kept in `result.html` (and in git history). The temporary "API test" button and `POST /api/echo` were removed.
- 2026-10-15: The `demo` and `demo-four` report ids are kept after step 3 (planned to be removed). Reason: the supervisor can see a four-dimension report while the rubric holds only Data.
- 2026-10-15: The intro and closing messages in `flow.py` are drafts by Claude, to be reviewed by the author.
- 2026-10-15: The chat page uses the author's new design (header, progress sidebar, bubbles, typing indicator, dimension dividers). The sidebar and the "Dimension x of n" counter are built from the rubric: `POST /api/conversations` returns an `outline` (dimension and subdimension names) and every response returns the `position` of the current subdimension. "View report" becomes active when the conversation is finished.
- 2026-10-15: Of the design's interactive extras, only the box shown with a follow-up is used (the design called it "checkpoint"; on the page it is labelled with the methodology terms: "Check", "Criteria covered", "Follow-up criterion"). It shows how many criteria the last check found covered and the criterion the follow-up targets; it is removed once answered. The sidebar counts scored subdimensions ("1 / 3 scored") and marks the current one. Quick-answer chips, "Skip", "I'm not sure" and "Save & exit" were left out. Reason: decided by the author; chips would suggest answers and bias the evidence, skipping and resuming are not part of the flow. Known trade-off: the check box shows respondents what is being assessed, which may steer their answers.
- 2026-10-18: The respondent may ask for clarification instead of answering. The check call recognizes this (`message_type`: `answer` or `clarification_request`) and its follow-up explains and asks the question again; no extra model call. Follow-ups are written by the model and may be personalised; opening questions stay fixed. Reason: decided by the author, so respondents who do not understand a question can still give evidence.
- 2026-10-18: Clarifications and follow-ups share the one limit `max_follow_ups` (2), so each subdimension has at most two chatbot messages after the opening question. Reason: decided by the author, to keep every subdimension short. Consequence: if the respondent asks a third time, the question is not answered; the subdimension is scored on what was said and the chatbot moves on.
- 2026-10-18: Rules for the model-written follow-ups (to go into `prompts/check.md`): a follow-up may refer to what the respondent said but asks about exactly one missing criterion, does not suggest an answer and does not assume facts the respondent did not state; a clarification explains only with the subdimension `definition` and plain wording, never gives examples of good practice and never mentions levels. Reason: decided by the author, so the chatbot does not lead respondents towards an answer or a level. FOR THE THESIS: discuss this as a trade-off of the chatbot format. Personalised follow-ups and explanations make the conversation easier to answer, but every respondent no longer gets exactly the same wording (unlike the questionnaire), and any explanation can still influence the answer. These rules limit that influence; the logs let it be checked.
- 2026-10-18: No check box on the chat page after a clarification request, only the re-asked question. Reason: the box shows criteria coverage, which is not what a clarification is about.
- 2026-10-18: The clarification rule is refined (replaces "a clarification explains only with the subdimension `definition`" in the entry above). A clarification replies to what the respondent actually asked, in the model's own words, then asks again. Three cases: a question about the meaning of the question or a term is answered using only the subdimension `definition` (not copied word for word); a question about the conversation itself (length, who sees the answers) gets "I don't know", nothing invented; an unrelated question gets a polite "I can't help with that here". In every case no examples of good practice, no levels, no suggested answers. Reason: decided by the author; a generic definition does not help a respondent who asked something specific. "I don't know" for questions about the conversation is for now; fixed facts can be given to the model later (for example with the consent screen in step 7). FOR THE THESIS: same trade-off as above; the explanations are personalised, so their wording differs between respondents.
- 2026-10-18: The fake chatbot's reply to a clarification request is a visible placeholder ("[fake] ...") instead of the definition. Reason: the fake cannot read the question, and the real reply will be personalised, so the placeholder should not look like real behaviour.
- 2026-10-18: Model provider OpenAI, model GPT-6.1 Sol (API id `gpt-6.1-sol` according to third-party listings). Reason: chosen by the author. Open: the fixed dated snapshot id (CLAUDE.md requires a dated version, not the alias), whether the model accepts temperature 0, and whether LangChain's OpenAI integration (`langchain-openai`) installs on Python Workers. All three are checked in step 4 before the first real call.
- 2026-10-18: LangChain test on Python Workers (no decision yet). The Cloudflare docs list only old built-in versions (langchain-core 0.1.25, langchain-openai 0.0.6, from 2024). Recent versions install from `pyproject.toml`: langchain-core 1.6.12 and langchain-openai 1.7.2 installed, and under `pywrangler dev` a `ChatOpenAI` call with `with_structured_output` (Pydantic model, temperature 0, model `gpt-6.1-sol`) reached OpenAI and got the expected 401 for a fake key. Catch: the Worker bundle grows from 2.4 MB to 7.1 MB compressed, which is over the 3 MB limit of the free Workers plan (paid plan: 10 MB). The test endpoint and the dependency were removed afterwards.
- 2026-10-18: Same test with OpenAI's own package (`openai` 3.35.1): installs and reaches OpenAI with structured output, but the bundle grows to 3.6 MB compressed, also over the 3 MB free-plan limit. Third test: a plain HTTP request to OpenAI's API with the Worker's built-in `fetch` (from `workers`), with the JSON schema generated from a Pydantic model. It reached OpenAI (expected 401 for a fake key) and adds nothing to the bundle (stays 2.4 MB). The author is on the free plan. Test endpoints and dependencies were removed afterwards; decision pending.
- 2026-10-20: The model is called with a plain HTTP request to OpenAI's Chat Completions API using the Worker's built-in `fetch`, not with LangChain or the `openai` package. The JSON schema for structured output is generated from the Pydantic models and the reply is validated with the same models. Reason: decided by the author; she is on the free Workers plan (3 MB limit) and both packages make the bundle too large (7.1 MB and 3.6 MB). Plain requests add nothing to the bundle and every step of the call is visible in the project's own code. Trade-off: switching provider means rewriting the one function that builds and sends the request, instead of changing a setting.
- 2026-10-20: Step 4. `prompts/check.md` and `prompts/score.md` are first drafts by Claude (version `0.1-draft`), to be rewritten by the author. The rubric texts are not copied into them: placeholders such as `{{criteria}}` and `{{levels}}` are filled from `rubric.json` for the current subdimension, so the same two files work for every dimension. The check prompt also gets the `plans` rule; the score prompt gets `score_values`, `mixed_evidence`, `plans` and `insufficient_evidence`. The filled prompt is sent as one message.
- 2026-10-20: `worker/src/llm.py` builds the prompt and the request body and checks the reply, but does not send anything; the Worker will send with `fetch` (step 5), the test script `worker/scripts/try_prompts.py` with urllib. Reason: the script runs on a normal computer, where the Worker's `fetch` does not exist, and this way both use the same prompt and checking code.
- 2026-10-20: The model returns the criteria as a list (criterion id, covered, quote), which code turns into the log's `{id: {...}}` shape after checking that exactly the rubric's criteria came back, in order. `all_covered` is worked out by code from the criteria, not by the model. Reason: the schema stays the same for every subdimension, and code does the logic, not the model.
- 2026-10-20: In the score, the model writes the evidence per criterion before the level. Reason: the level should follow from the evidence it has written down, not the other way round. The log keeps the order from CLAUDE.md (level first).
- 2026-10-20: The exact model version that answered (the `model` field of OpenAI's reply) is read from every reply, so it can be logged even if the model id is an alias. Reason: no dated snapshot id of GPT-6.1 Sol has been confirmed yet.
- 2026-10-20: Open for step 5: the prompts are in `prompts/` at the top of the repository (as in the layout in CLAUDE.md), but the Worker only bundles files from `worker/src/`. They will need to move there or be copied, like the rubric.
- 2026-10-20: CORRECTION. The size limits used in the three entries above (3 MB free, 10 MB paid, compressed) were out of date. Cloudflare's limits page now gives 64 MiB uncompressed for both plans and no compressed limit. Measured uncompressed: plain request 9.2 MiB, `openai` package 18.4 MiB, LangChain 32.7 MiB, so all three would deploy on the free plan. The decision for plain requests was based on this mistake and is replaced by the next entry.
- 2026-10-20: The model is called with OpenAI's own Python package (`openai` 3.35.1), not LangChain and not plain requests. The Pydantic models are passed to `client.chat.completions.parse`, which sends the JSON schema and validates the reply. Reason: decided by the author. Compared with plain requests, the package handles the request and the reply; compared with LangChain, it is about half the size and one layer less to explain. Trade-off: switching provider means rewriting `call_model` in `llm.py`. This also replaces the urllib/fetch split in the step 4 entry: the Worker and the test script now both call `llm.call_model`.
